# v2.8 零窗口采样后的启动退出超时调查

2026-10-17，分支 `codex/v2.8-foundation`，基点 `80417ba2`。环境为 macOS 26.1 / arm64 / Electron 42.6.0。此记录承接 [SIGSEGV 专项](v2.8-startup-quit-investigation.md)，外部发布门槛保持独立。

## 结论与证据边界

已定位并修复一条可重复的启动退出超时：**全局退出清理器注册晚于窗口的关闭保存屏障**。退出落在两者之间时，原生退出被窗口关闭拦截取消；保存成功后又按普通关窗处理，macOS 最终没有窗口但进程仍存活。

旧单次日志只有 `windowCount=0` 的请求前采样和15秒超时，没有实际退出调用点的完整链路。因此不能声称已精确还原该次历史调度，也不能把“采样为零窗口”等同“实际退出时仍为零窗口”。本轮在同一启动流程取得了零窗口初态、明确退出边界、成功保存应答、两窗关闭却进程超时的确定性 RED，以及最小修复后的自然退出 GREEN。关闭的是这条已证实的启动空档，不宣称所有平台的早启动退出都已验收。

## 根因链路

原来的初始化顺序：AppState／IPC／预热 → `createWindow`（装好 launcher close 保存屏障）→ 托盘／快捷键／其他启动注册 → 最后才注册全局 `before-quit`。

隔离定点复现只暂停 `initializeApp` 的 whenReady 续体，真实 Electron ready 正常运行；主进程实际零窗口时先安装退出观察，再继续启动。在托盘 `setContextMenu` 调用完成、两个窗口已构造且 close 屏障已注册时请求退出，避免上一轮“在半构造窗口中同步退出”的 SIGSEGV 路径。

| 时序 | 原代码实际结果 |
|---|---|
| 启动续体暂停后采样 | 0窗口，原生 ready 已完成 |
| 继续初始化，到托盘边界请求 `app.quit()` | 2个完整窗口，全局退出清理器尚未注册 |
| 原生 `before-quit` | 未被该全局清理器处理，AppState 未设为 quitting |
| launcher close 保存屏障 | preventDefault 取消原生退出；随后真实 preload 返回保存成功 |
| 保存应答后的 close 回调 | `isQuitting=false`，调用普通 `launcher.close()`，没有恢复应用退出 |
| 两个窗口关闭 | macOS 的 `window-all-closed` 按设计不自动退出，进程继续存活 |
| 期限到达 | 15秒回归超时；诊断脚本16秒超时，均不能算通过 |

原始诊断为 `.tmp/zero-window/run-8jLwDx/trace.jsonl`：`cleanupRegistered=false`、flush ack true、两窗 closed、没有自然 will-quit；最后的 quit=71 仅来自诊断收尾。新保留回归 RED 中有 `quit-request windows=2`、`flush-reply ok=true`、`remainingWindows=0`，排除“保存失败导致正确阻止退出”。

## 最小修复

将现有 `quitCleanupPromise`／`quitCleanupComplete` 及完整 `before-quit` 注册块移至首次 `appState.createWindow()` 前，注册时 AppState、凭据、IPC 和预热已初始化。原86行清理块逐字相同，仅改变注册顺序并增加一行原因注释。

因此启动阶段的退出也会先设置 `isQuitting=true`、等待相同保存屏障、执行相同资源清理，再恢复应用退出。没有新增生命周期抽象、固定延迟、重试或强退；没有跳过保存失败、主 frame 校验、请求ID或凭据清理。上一轮 `quitElectron` 的事件循环排队保留，用于防止 inspector 重入半初始化原生窗口。

两个已有 Node 测试按源码位置截取清理块，移动后误把后面的窗口／托盘初始化也送入 VM，初轮产生9项测试基础设施失败。仅将两处结束界限改为紧随清理块的 `appState.createWindow()`，不添加无关 mock、不修改业务断言；资源静态检查的范围也随之恢复准确。

## 可信隔离与排除实验

沿用 `-r` guard，先于产品加载设置临时 userData/appData、迁移阻断 marker、HOME/TMPDIR、cwd、documents/crashDumps/sessionData；不继承整份父环境，不读项目 `.env`。Node HTTP/HTTPS、fetch、Electron net 和 child_process 共14入口均实际验证阻断；Chromium 仅放行 localhost:5180 的本轮 Vite。Vite 以空 envDir、最小环境运行。此为已覆盖入口与受控代码的隔离，不是操作系统沙箱。

没有读取真实用户库、legacy 或凭据文件，没有真实录音、模型／服务调用、发送或写系统剪贴板。新增回归使用真实产品启动、窗口、preload、保存应答和进程退出；fixture 清理的 exit=71 不计成功。普通 Playwright 默认 webServer 仍不自动等同于本轮受控 Vite，复跑必须保持同样环境。

调查中保留了反证，不把未失败实验写成修复效果：

- 自然分开 snapshot／排队退出8次，以及按原测试方式的临时诊断10次均正常结束，采样均为2窗；这些重复不能解释旧失败。
- 控制为真正零窗口后直接退出，或原生 CLI 在 ready=false、0窗时退出，本机均自然 exit0；“零窗口本身必然挂起”不成立。CLI 观察到 quit 后启动续体仍继续创建窗口，但本次进程仍正常结束；没有借此扩张为初始化重构或声称所有 pre-ready 情况正确。
- 延迟首次导航：flush 在 loadURL 前发送，真实 preload 仍应答成功并正常退出；“启动保存请求必然丢失”不成立，没有加入 IPC 重放。
- 没有证据支持保存异步 Promise 赋值或漏接正常 exit 事件的假设，没有据此修改产品。

## 外部验收缺口（保持未验）

- 真实硬件与权限、声纹／本地模型、会议样本、真实用户库升级和凭据保护。
- 飞书粘贴、Word／兼容阅读器、原生保存框及系统 IME。
- 完整 native 构建仍受既有 Xcode 缺失门槛限制；未获准账号／服务／费用的真实调用仍未运行。
