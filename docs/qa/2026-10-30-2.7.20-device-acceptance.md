## 本次追问：QCLOUD 是否需要专门的语音 Key

不需要另申请一份语音专用 Key。`SpeechStep.tsx` 的 `qcloud-stt` 写入 `setNativelyApiKey`，`OnboardingConfiguration.ts` 也将该服务的凭据映射到 `nativelyApiKey`。AI 服务使用同一凭据；账号仍须拥有相应语音和模型调用权限。首次从未配置过时需要填写 Key。

发现配置复用疑点：语音页的空 Key 校验取决于已保存服务的 `check.configured`、`check.provider` 和 `changingKey`，切换到 QCLOUD 时可能在已有共享 Key 的情况下仍要求重复输入。这是源码可确认的校验路径，尚未用已保存真实 Key 的发行态实例完成复现，不应解释为云端需要两套 Key。2.7.20 发行包验收阶段只记录，未修改实现；后续工作区修复见本文末节。

用户截图中“所选语言不受支持”的提示也不能直接证明 QCLOUD 不支持中文：页面同时存在未保存的服务选择和已保存服务的检查状态，需要单独复现确认提示是否滞后。

## 2026-10-30 后续源码修复：共享密钥与语言提示（尚未发布）

本节记录在 2.7.20 安装验收之后的工作区修复；上面的发行包观察和未完成真机项目保持原结果。当前 `/Applications/CueUp.app` 仍为已发布的 2.7.20，不包含本节修复。

### 根因与修正

1. 首次设置的语音页与 AI 页都用“当前已保存 provider 是否配置”判断是否必须填 Key。当其他服务处于默认状态时，选择 QCLOUD 不能发现已经保存的共享 `nativelyApiKey`。现在主进程在现有 onboarding snapshot 中仅提供 `qcloudKeyConfigured` 布尔值，两个页面据此复用凭据；不会为展示状态调用返回密钥正文的 API，也不创建新密钥字段或改动存储格式。
2. 显式点击“更换密钥”仍要求输入新值；切换到其他服务再切回时退出更换模式，沿用已保存共享密钥。没有保存过密钥时仍保留必填提示与焦点定位。界面注明语音识别与 AI 共用 QCLOUD API Key。
3. 语音页之前直接展示 `snapshot.checks.stt` 的结果，而下拉选择是尚未保存的草稿。现在检查结果与 provider、会议语言及 Whisper 模型相符时才展示；改动选择后显示“配置已更改，保存后重新检查。”，不沿用旧成功回执、检查深度或语言错误。恢复原选择时可再次展示匹配的检查结果。AI 页也只展示与当前服务及模型一致的检查状态，避免共享密钥已保存却仍显示旧服务缺少凭据。模型下载状态按当前模型展示，更改会议语言不隐藏真实下载进度。
4. 主进程在读取新配置身份时，曾保留上一次被动检查的语言错误。现在旧语言错误不能附着到新的配置身份上；重新刷新仍按实际配置计算兼容性，未把“不显示旧错误”当成验证通过。

QCLOUD 语音通道在当前实现中支持 `chinese` 及 `auto`（中文优先），英文等其他选择仍按现有兼容性规则提示不支持。本次不扩大识别服务的语言能力。用户中文截图中的旧提示已用“服务/语言草稿与保存检查不一致”的回归路径复现。
