# RAG 可用性与中文回答修复设计

## 背景与目标

当前会议搜索和全局搜索存在两类用户可见问题：

1. RAG 初始化失败后持续降级为普通聊天，无法稳定使用向量检索。
2. 无论用户输入中文、英文还是 `KPI` 等缩写，回答可能为英文。

本次目标是恢复已打包应用中的 RAG 可用性，并保证当前会议搜索、全局搜索及其降级路径始终使用简体中文回答。

## 已确认的根因

### 1. 不完整的用户模型目录遮蔽内置模型

`LocalEmbeddingProvider` 目前只要发现用户数据目录存在，就优先使用该目录；它没有验证 ONNX 模型等必需文件是否完整。日志显示用户目录缺少 `onnx/model_int8.onnx`，而已安装应用的 `Resources/models` 中存在完整模型。因此，一个残留或下载中断的目录会错误遮蔽可用的内置模型。

### 2. sqlite-vec 动态库路径解析失败

`sqlite-vec.getLoadablePath()` 通过包子路径解析 `vec0.dylib`。当前平台包的 `exports` 未公开该子路径，导致 `ERR_PACKAGE_PATH_NOT_EXPORTED`。应用随后只能退回 JavaScript 余弦相似度。

### 3. 打包后的向量 Worker 缺少运行时依赖

向量检索 Worker 在已安装应用中加载 `better-sqlite3` 时找不到 `bindings`。当前 `asarUnpack` 解包了原生二进制和 Worker，但没有保证 `bindings` 及其依赖 `file-uri-to-path` 与 Worker 一起可访问。

### 4. 回答语言约束不完整

会议 RAG、全局 RAG 和降级聊天使用不同提示词。现有提示词为英文，且没有“始终使用简体中文回答”的强制约束，所以 `KPI`、英文问题或检索未命中时容易得到英文回答。

## 方案

### 模型选择

在选择模型目录前验证完整性，至少检查配置、分词器和 `onnx/model_int8.onnx`。目录完整性验证只能证明文件存在，不能证明模型能够被当前版本的 Transformers.js、ONNX Runtime 和系统架构正常加载。因此，选中用户模型后还必须完成一次运行时可用性验证。

运行时可用性验证包含：

1. 从用户模型目录创建 `feature-extraction` Pipeline。
2. 使用固定、无用户数据的短文本执行一次 Embedding。
3. 验证输出维度为 `384`，且所有数值均为有限数。

选择顺序保持不变：

1. 用户下载模型完整时使用用户目录。
2. 用户目录不完整而应用内模型完整时，自动使用应用内模型。
3. 两处都不完整时，返回包含已检查目录的明确初始化错误。

不自动删除用户目录，也不改变模型下载流程。

### 升级安装时的模型处理与可用性验证

Embedding 模型分为两类，升级时必须分别处理：

- **用户下载模型**：位于 `app.getPath('userData')/models`。该目录独立于应用安装目录，覆盖安装和自动更新不得删除、覆盖或重复下载其中的模型。Windows 安装器继续保持 `deleteAppDataOnUninstall: false`。
- **应用内置模型**：位于已安装应用的 `Resources/models`。它属于应用发布资产，升级安装时随新版本应用一起替换。

安装包中的 `postinstall.js` 只在开发或 CI 安装依赖、制作发布包时下载内置模型，不会在最终用户安装或升级应用时执行。因此，用户升级时不应依赖网络重新下载 Embedding 模型。

安装器阶段不直接加载 ONNX 模型。macOS 当前可能由用户手动覆盖安装，Windows 安装器也不应承担应用运行时模型推理。因此，“升级时验证”定义为：**新版应用升级后的首次启动，在 RAG 初始化过程中验证用户模型的完整性和真实运行可用性**。验证不得使用会议内容、用户问题或其他用户数据。

升级完成后的模型选择规则为：

1. 已有用户模型文件完整且运行时验证通过时，继续复用该模型，不重复下载。
2. 已有用户模型目录存在但文件不完整，或模型无法加载、推理、输出合法的 `384` 维向量时，保留该目录，不进行破坏性清理，并自动验证和使用新版应用内置模型。
3. 用户模型缺失时，验证并使用新版应用内置模型。
4. 用户模型和内置模型均无法通过验证时，RAG 初始化失败并返回可诊断错误，不静默宣称 RAG 可用。

验证结果应写入安全日志和质量诊断信息，只记录模型来源、验证阶段、错误类型和应用版本，不记录测试文本、文件内容、用户目录绝对路径或其他用户数据。同一应用版本、同一模型文件状态下不应在每次查询时重复执行验证；首次初始化验证通过后在当前进程内复用已加载的 Pipeline。

当前版本继续使用相同的 `Xenova/paraphrase-multilingual-MiniLM-L12-v2` 模型，因此完整的已有模型可以直接复用。本次不增加模型版本迁移或哈希升级机制；如果未来更换模型 ID、模型文件或 Embedding 维度，应另行设计模型清单、版本和向量重建策略。

### sqlite-vec 加载

保留官方 `getLoadablePath()` 为首选；当它因包导出规则失败时，根据当前平台与架构定位同级平台包中的 `vec0` 动态库。继续应用现有的 `app.asar` 到 `app.asar.unpacked` 转换和扩展名处理。

若动态库确实不存在，维持当前 JavaScript 余弦降级能力并记录可诊断错误。

### Worker 打包

将 `bindings` 和 `file-uri-to-path` 加入 `asarUnpack`。增加发布资产校验脚本，在 macOS ARM64、macOS Intel 和 Windows 构建进入打包前验证：

- 内置 RAG ONNX 模型存在；
- Worker 所需模块可解析；
- sqlite-vec 对应平台包存在。

这样 CI 会在生成安装包之前失败，而不是把不可用的 RAG 发布给用户。

### 中文回答

在以下入口统一添加最高优先级约束：始终使用简体中文回答；专业缩写可保留原文，但解释必须为中文。

- 会议 RAG 系统提示词；
- 全局 RAG 系统提示词；
- 会议搜索的普通聊天降级提示词；
- 全局搜索的普通聊天降级提示词。

不根据输入语言切换回答语言。

## 验证标准

自动化测试必须覆盖：

1. 用户模型目录存在但缺少 ONNX 文件时选择完整的内置模型。
2. 用户模型完整时仍优先选择用户模型。
3. 模拟升级后的首次启动时，完整且可加载的用户模型通过固定短文本推理，产生合法的 `384` 维有限数向量，并且不会触发重新下载。
4. 用户模型文件完整但加载失败、推理失败、维度错误或包含非有限数时，保留用户模型并自动使用通过验证的内置模型。
5. 用户模型目录不完整时保持目录不变，但运行时选择通过验证的新版内置模型。
6. 用户模型和内置模型均验证失败时，RAG 明确报告不可用，诊断日志不包含用户数据或绝对路径。
7. `getLoadablePath()` 触发包导出错误时可解析平台动态库。
8. 打包配置包含 Worker 的运行时依赖，发布资产校验能发现缺失模型。
9. 中文问题、英文问题和纯缩写问题在会议/全局 RAG 及降级路径中都带有强制中文约束。
10. Electron 类型检查、相关单元测试和生产构建通过。

## 非目标

- 不调整检索排序、分块策略或召回阈值。
- 不重构 Provider Router。
- 不删除用户已有模型文件。
- 不引入模型版本迁移、哈希更新或自动清理机制。
- 不把普通聊天降级伪装成 RAG 命中。
