# 会议准备模式推荐契约强化设计

## 背景

AI 会前准备目前允许在 `sales`、`fde`、`recruiting` 和 `team-meet` 中推荐一个主模式，并已向模型提供主题、客户、参会人、目标、议程和背景。现有提示词只规定“技术与交付型客户会议优先 FDE，商务与价值沟通优先 Sales”，没有规定信息冲突时的判断顺序，也没有覆盖常见边界场景。

因此，“售前技术交流”可能因“售前”被推荐为 Sales，也可能因“技术交流”被推荐为 FDE；“首次向管理层做解决方案汇报”也可能因为包含技术内容而被误判为 FDE。推荐结果依赖模型对模糊词语的自由解释，缺少稳定的产品契约。

## 目标

强化模式推荐提示词，使模型按照会议的主任务而非单个关键词选择模式，并明确以下结果：

- 售前技术交流、技术验证、集成讨论默认推荐 `fde`；
- 首次向客户管理层进行解决方案与价值汇报默认推荐 `sales`；
- CTO 或技术委员会进行技术方案评审默认推荐 `fde`；
- 预算、决策链、商务异议和采购推进默认推荐 `sales`；
- 招聘流程只推荐 `recruiting`；
- 内部协作只推荐 `team-meet`，外部客户会议不得推荐 `team-meet`。

## 方案比较

### 方案 A：强化提示词契约（采用）

在 `buildModePrompt` 中加入判定优先级、模式边界、冲突处理原则和少量关键示例。保持现有输入、输出 Schema、数据库和页面不变。

优点是改动小，与当前 AI 推荐机制一致；缺点是提示词不能提供数学意义上的完全确定性。

### 方案 B：在服务层硬编码关键词分类

根据“技术交流”“管理层”“报价”等关键词直接决定模式。该方案看似确定，但无法可靠理解否定、混合议程和真实会议目标，容易形成另一套与提示词冲突的分类系统，因此不采用。

### 方案 C：扩展返回结构并引入置信度与追问

让 AI 返回候选模式、置信度和缺失信息，低置信度时要求用户补充信息。该方案可能改善长期体验，但需要修改 Schema、数据库和页面，超过本次修正范围，因此不采用。

## 推荐契约

`buildModePrompt` 应明确要求模型依据会议的主任务判断，而不是依据单个关键词，并使用以下优先级：

```text
会议目标 > 议程 > 参会人 > 主题名称
```

判定规则如下：

1. 明确属于内部协作时推荐 `team-meet`。
2. 明确涉及候选人或招聘流程时推荐 `recruiting`。
3. 对于外部客户会议：
   - 核心任务是技术需求发现、产品能力确认、集成、安全、部署、交付风险或成功标准时推荐 `fde`；
   - 核心任务是解决方案价值汇报、管理层认可、预算、决策链、商务异议或采购推进时推荐 `sales`。
4. “售前”本身不等于 `sales`。售前技术交流归入 `fde`，管理层方案与价值汇报归入 `sales`。
5. 同时包含销售和技术内容时，按照会议结束时希望达成的主要结果选择一个主模式。

提示词应包含四个边界示例，但示例只用于解释规则，不改变现有 JSON 输出格式：

- 首次与客户研发负责人做产品技术交流 → `fde`；
- 首次向客户管理层做解决方案汇报 → `sales`；
- 向 CTO 和架构团队做技术方案评审 → `fde`；
- 处理报价异议并确认采购流程 → `sales`。

## 数据流与范围

数据流保持不变：

```text
六字段会议上下文
  → buildModePrompt
  → 当前选中的 LLM
  → { templateType, reason, focus }
  → Schema 校验
  → 用户确认或手动切换模式
```

本次只修改：

- `electron/services/meeting-preparation/MeetingPreparationPrompts.ts`
- `electron/services/__tests__/MeetingPreparationService.test.mjs`

本次不修改 Schema、数据库、IPC、模型路由、页面、模式定义或准备结果生成逻辑。

## 错误处理

保持现有错误处理：模型必须返回 `templateType`、`reason` 和 `focus`；返回不支持的模式或非法 JSON 时继续由现有 Schema 拒绝。用户仍可在确认步骤手动切换推荐模式。

不增加静默回退或关键词覆盖，避免界面展示的 AI 推荐理由与实际选中模式不一致。

## 测试与验收

采用提示词契约测试锁定以下内容：

- 明确存在“会议目标 > 议程 > 参会人 > 主题名称”的优先级；
- 售前技术交流映射到 `fde`；
- 首次向客户管理层做解决方案汇报映射到 `sales`；
- CTO 技术方案评审映射到 `fde`；
- 报价异议和采购推进映射到 `sales`；
- 外部客户会议不得推荐 `team-meet`，招聘与内部协作边界继续保留。

实施时先新增测试并确认旧提示词失败，再进行最小提示词修改并确认定向测试通过。随后运行 Electron 类型检查和完整项目测试，确保提示词变更没有影响会议准备的其他流程。

## 已知限制

提示词强化可以显著降低边界场景的随机性，但不能保证所有模型在所有输入下都严格遵循规则。本次接受该限制，因为用户可以在确认步骤纠正模式，且当前目标是用最小改动建立清晰、可回归的产品契约。若后续真实使用仍出现高频误判，再单独评估确定性分类或低置信度追问机制。
