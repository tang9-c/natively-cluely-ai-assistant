# 如何用顾问式方法开好一场客户会

> 本文根据 CueUp 的公开使用文档、架构说明和本机安装版界面编写。文中展示的是产品入口和一套可练习的会议方法，没有把它写成客户项目案例，也没有对转写准确率、成交率或会议效率作量化承诺。

客户会开到一半才发现三个问题没有想清楚，往往比准备得不够漂亮更难处理。

客户现在最急的是什么。我们手里有哪些能核对的材料。今天结束时，双方准备把哪一件事往前推。

很多人把这些问题留到现场。客户一抛出“你们能不能和现有系统打通”，销售就开始讲功能；技术同事接着补架构；半小时过去，大家还没问清楚对方要打通的流程、数据边界和验收条件。会后纪要写得再完整，也补不回当时应该问出口的问题。

顾问式会议的价值，在于让对话沿着事实、判断和行动往前走。它不要求每个人都学咨询公司的话术，更不需要带着一大摞模板进会议室。你只要在会前把问题收窄，会中把信息分层，会后让负责人和下一步落到纸面上。

CueUp 适合放在这套工作法里。它能记录会议，也能帮助用户在会前整理背景、在会中按场景获得提问和核对建议、在会后找回资料和行动项。工具本身不会替人判断，使用者仍要对每一句对外表达负责。

## 先把会议从“介绍产品”改成“确认一个问题”

一场客户会之前，我建议先写下一句话。

> 今天这场会结束时，我们希望确认什么。

它不是会议主题。会议主题可以写“智能制造方案交流”“项目启动沟通”。这句话要落到可判断的状态，例如客户是否认可先做某个业务流程，是否愿意补齐接口清单，是否同意安排下一次技术评审。

这一步会逼着人做取舍。客户刚提出一个大而模糊的需求，今天很难同时谈清业务价值、产品范围、部署条件、预算、合同和排期。把目标写成一个可确认的问题，会议才有主线。

接下来用三张小纸条准备材料。

| 会前要写下的内容 | 会议里用来做什么 |
| --- | --- |
| 已知事实 | 客户现状、已确认的问题、旧系统、已承诺事项 |
| 需要验证的判断 | 痛点是否真实、范围是否合适、谁有决策权、条件能否满足 |
| 希望形成的行动 | 谁补资料、谁安排评审、下一次讨论什么、日期由谁确认 |

这三类内容混在一起，会议很容易变成各自发言。把它们分开，销售负责推动判断，技术同事负责澄清条件，项目负责人负责收住行动。每个人都知道自己为什么要问这个问题。

CueUp 的“会议作战准备卡”提供了一个很适合做这件事的入口。用户可以输入或直接说出客户、对象、目标、议程和背景，系统把内容拆成可编辑字段。它也可以关联历史会议，并提示可能的问题和资料状态。

![CueUp 的会议作战准备卡](images/zhihu/meeting-preparation.png)

*图 1 展示本机安装版的会前准备入口。文字和语音内容都可以在进入下一步前修改。*

建议在系统拆解以后逐项改一遍。客户名称、目标和背景都不难填，人要盯住的是那句“本次希望确认什么”。它写不清楚，后面的建议和资料检索都会失去焦点。

会前准备也有明确边界。它不会自动同步 CRM 或日历，也不会把准备结果悄悄塞进之后的每一次回答。对于报价、交付和合规，这种克制反而更可靠。资料可以帮助你提问，承诺仍要由人核对后说出口。

## 会中沿着三条线听，不让客户的问题被产品介绍冲走

客户会里最常见的失误，是听到一个问题就急着回答。顾问式的做法会慢半步，先判断这个问题属于哪一条线。

第一条线是事实。客户的流程怎么跑，哪些系统正在用，问题在什么时间出现，谁受影响，已有数据在哪里。

第二条线是判断。客户为什么现在要解决，什么结果算成功，哪些约束不能碰，谁参与决策，预算和排期是否真的进入讨论。

第三条线是行动。下一步需要谁提供什么，什么材料要先核对，下一场会要解决哪个问题，谁对日期负责。

以一次常见的销售发现会为例。客户问“你们和现有 PLM 能不能集成”，先不要急着说“支持 API”。可以先问四句。

1. 目前要打通的是哪一段流程，从谁开始，到谁结束。
2. 需要同步哪些对象和字段，哪些数据只读就够。
3. 现有系统由谁维护，接口和权限资料谁能提供。
4. 客户希望用什么标准判断这次集成是否成功。

这四句把模糊的“能不能”收成了流程、数据、责任和验收条件。技术回答到这里才有位置。客户也更容易判断你是否听清了问题。

CueUp 的会议模式可以给这类注意力分配一个稳定的默认方向。当前版本提供通用、销售、FDE、招聘、团队会议、求职、技术面试和讲座八种内置模式。销售模式会关注需求、异议、产品反馈和跟进；FDE 模式会更重视工作流、技术约束、风险和下一步。

![CueUp 的销售模式配置界面](images/zhihu/mode-settings.png)

*图 2 展示销售模式的配置页。用户可维护自定义上下文、意图词和会后笔记分区。*

模式会决定系统在实时对话里更容易注意什么，也会改变会后记录怎样组织。它不能充当事实校验器。面对价格、法规、交付范围和客户承诺，仍要回到原始资料和会议原文。

## 工具怎样帮上忙 让问题带着证据出现

会议里的好建议，应该能回答两个问题。

这句话为什么现在要说。它凭什么成立。

CueUp 会把实时转写、当前模式和可用的知识片段作为会中辅助的输入。用户也可以在输入框直接提问，例如请系统给一个澄清问题，梳理刚才确认的行动项，或者回应客户对集成工作量的顾虑。需要看屏幕内容时，还可以使用截图提问，但这要求系统权限和对应数据范围都已允许。

动态卡片是另一种入口。它只在当前模式、实时会议信号和可用证据同时满足条件时出现。卡片可能是回应建议、检查清单、跟进草稿、行动项或决策记录。它们不是每句话都会弹出，同一时刻最多显示三张，用户可以接受、忽略或修改。

这个设计很适合会议里一个容易被忽略的动作。看到建议时，先找依据，再决定要不要用。能说出口的文字不等于能对客户承诺的文字。把卡片当成一个提醒和草稿，通常比把它当作自动回答器更安全。

资料库和业务系统知识源会让这个过程更扎实。CueUp 可以索引 PDF、DOCX、Markdown、TXT 和 PPTX，在问题发生时检索相关片段。Embedding 暂时不可用时，系统会回退到关键词和中文 n-gram 检索。资料没有完成索引之前，不应期待它被会中问答可靠引用。

![CueUp 的知识源与资料库设置页面](images/zhihu/knowledge-sources.png)

*图 3 展示知识源页面。本机截图中的 API Key 由应用界面掩码显示，未包含原始密钥。*

业务系统知识源通过 MCP 发现服务端提供的只读工具和参数 schema。以 Windchill、QMS 一类系统为例，CueUp 可以把查询结果作为会议中的证据片段，但不会替用户创建、更新、审批或提交业务记录。这样的安排很符合客户会的现实。会议里需要的是查清状态、核对边界和确认下一步，真正的写入和审批应当回到原系统完成。

## 一套可以明天就开始练的会议节奏

下面这套节奏适合销售发现会、方案沟通和技术澄清会。它不会替代专业判断，但可以让第一次练习有一个清晰起点。

会前一天，把会议主题写成一个待确认的问题。用 CueUp 的会前准备入口整理客户、目标、参会人和已知背景。只上传本次会真正要用的方案、案例、规范或项目材料。资料越多，越需要先判断哪些会影响本次问题。

会议开始前，选一个贴近实际角色的模式。销售会就选销售，现场调研和交付推进就选 FDE。启动后先看滚动转写是否持续更新。没有稳定转写，后面的问答和动态卡片缺少输入，不能指望它们给出可靠建议。

客户提出关键问题时，先按事实、判断、行动三条线记下来。不要急着追求一句漂亮的回答。优先问清流程、条件、责任和验收标准。系统检索到资料时，打开原始文件或业务记录核对版本、时间和适用范围。

会议快结束时，把行动项读一遍。每一项至少包含动作、负责人和下次确认点。CueUp 会后记录可汇总会议概述、关键要点、决策、行动项和待确认事项，也支持全文搜索与可编辑 DOCX 导出。导出前仍应看一遍，尤其是客户名称、数字、日期和对外承诺。

## 会议工具要帮人把问题往前推进

顾问式工作法关心一件具体的事。会议工具能否帮助团队在有限时间内，把一个模糊问题变成几个可以验证、可以分工、可以继续推进的问题。

CueUp 在这个过程里有三个实用位置。会前把材料和目标收拢，会中让提问、资料和模式保持相关，会后把行动和证据留给下一次沟通。它解决不了客户的业务难题，也不能替人承担报价、技术和合规风险。它能减少一些低价值的翻找、遗漏和重复解释，让人把注意力留给真正需要判断的地方。

如果你想试这套方法，可以从一场低风险客户会开始。只设一个会议目标，只准备几份已确认的资料，只观察一个问题。会议结束后回头看，问题是否问得更早，承诺是否留得更清楚，再核对资料是否真的帮上了忙。把这些留下来，下一场会才会比上一场更好。
