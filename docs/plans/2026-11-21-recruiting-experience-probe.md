# 招聘场景优化方案 · 结构化面试与会后复盘（修订版）

2026-11-22 修订，待实施。首个端到端验收场景为 B2B 新客销售岗业务一面。

## 2026-11-22 决策：先以岗位技能试用（第零阶段）

第一、二阶段的模板只在会后导出时使用，因此先不做会前选模板、数据库列和主进程改动。五套预置模板各做成一个内置技能，放在 `resources/skills/interview-review-*`，由技能管理器自动安装。面试官在会议详情的转写技能菜单里按岗位选择即可；没有对应岗位时继续用 `interview-evaluation`。

| 技能 id | 模板 |
|---|---|
| `interview-review-b2b-sales` | B2B 销售（新客开拓） |
| `interview-review-product-manager` | 产品经理 |
| `interview-review-enterprise-consultant` | 企业系统业务顾问 |
| `interview-review-enterprise-project-manager` | 企业系统项目经理 |
| `interview-review-software-engineer` | 开发工程师 |

用户复制技能文件夹并修改 `SKILL.md`，即可得到自定义模板或兼岗模板，以此替代第二阶段的编辑器。五个文件共用同一套整理规则，修改规则时需同步更新五份。试用反馈确认内容有效后，再决定是否实施下文的第一至三阶段。届时注意：模板不能拼在转写前面，因为长转写分段时只有第一段能看到模板，汇总时也看不到；应通过每次调用都会带上的指令传入。

## 修订说明

原方案一次引入四个新系统：可编辑岗位模板、会中维度覆盖跟踪、自动开题和经历追问卡。按代码现状复核后，本版先交付"会前选模板 → 会后按同一标准复盘"的闭环，会中实时能力后置。主要调整如下。

| 原方案 | 本版处理 | 原因 |
|---|---|---|
| 会中自动开题、维度覆盖状态机 | 后置到第三阶段 | 需实时判断话题收束、同义提问和证据覆盖，每轮都要语义判定，收益最不确定 |
| 维度权重 | 第一、二阶段不做 | 评分由面试官填写，没有加权汇总，权重只用于展示 |
| 完整模板编辑器（增删维度、排序、必问、权重、逐分锚点） | 第一阶段只读预置模板；第二阶段支持"复制预置模板后改文字" | 编辑器体量大，复制改文字已覆盖主要诉求 |
| 经历追问卡按"连续项目讨论"去重 | 后置；届时复用现有同类卡冷却和关闭冷却 | 代码中没有项目段落切分能力，方案也未定义切分方式 |
| 异步重判（暂缓展示、用新上下文重判） | 后置；届时复用现有"新转写中止旧判定"机制 | `IntelligenceEngine.ts` 已对同一会话的新文本中止旧判定 |
| 试用指标（人工标注回放统计） | 放到试用阶段 | 需要标注数据，不阻塞首版交付 |

## 三个模块的分工

| 模块 | 职责与交接 |
|---|---|
| 档案智能 → 场景档案 | 提供招聘模式下的 JD、简历、公司背景。招聘方个人主档不能作为候选人经历。招聘视角的会中检索和会后纪要检索都排除评分卡、评分标准和练习题，包括已经上传的旧文件。 |
| 模式设置 → 招聘场景 | 第一阶段提供五套只读预置模板；会前选定本场模板。第二阶段支持复制后改文字。 |
| 技能 → 招聘面试复盘 | 面试官从会议详情的现有转写技能入口运行 interview-evaluation。导出服务按 `meetingId` 找到本场模板，与转写一并交给技能，生成 Markdown 并返回路径。评分和综合意见由面试官在导出文件中填写。 |

## 第一阶段：会前选模板，会后按同一标准复盘

目标是打通"选模板 → 随会议保存 → 导出时取回"这一条链路，不改会中实时链路。

1. **预置模板（只读）。** 五套模板以代码常量形式随应用发布，每套有稳定的 `id`、名称、维度顺序、标准主问题和 1–4 分行为锚点，内容见下文"五套预置岗位模板"。不建模板表，不做编辑。
2. **会前选择。** 招聘模式下，在模式选择旁增加"本场面试模板"选项，默认不选。选择结果存为主进程设置（与当前模式并列），不经过会前准备页，也不需要渲染端在 `startMeeting` 时传参。
3. **随会议保存。** 主进程 `startMeeting` 在招聘模式下读取该设置，写入会议元数据 `interviewTemplateId`。`meetings` 表新增可空列 `interview_template_id`，沿 `SessionTracker` 元数据 → `MeetingPersistence` → `saveMeeting` 的现有路径写入，做法与 `calendarEventId` 相同。迁移编号用 v40（v39 已被本地未推送的弹卡改动占用）；实施前与其他进行中的分支核对编号，避免冲突。
4. **导出时取回。** `runTranscriptSkillExport` 在技能为 interview-evaluation 时，用渲染端已传入的 `meetingId` 读取该会议的 `interview_template_id`，把模板转成 Markdown 段落放在转写之前一并交给技能。找不到模板时不拼接，技能按现有规则注明"未提供本场模板"。渲染端无需改动。
5. **排除旧评分类资料。** 新增一个"取可检索参考文件"的辅助方法：当前模式为招聘、招聘方视角时，跳过 `mode_reference_file_metadata.doc_subtype` 为 `scorecard`、`rubric`、`practice-problem` 的文件。只在 `ModesManager.ts:555/579/670/696` 这 4 个检索调用处改用它，会中回答和会后纪要同时生效。`getReferenceFiles` 本身不变，设置页仍列出全部文件，用户可以查看和删除旧资料。
6. **技能说明对齐。** `interview-evaluation/SKILL.md` 中"模板及版本"改为"模板名称"；第一阶段模板只读，不涉及版本。

### 第一阶段验收

前提：会议保留策略不能是"从不保存"。该策略下会议不落库，无法会后导出。

1. 会前选择销售模板并开会，结束后在数据库中核对该会议的 `interview_template_id`。设置页的参考文件列表和文件计数仍包含旧评分卡等全部文件。
2. 把界面当前选项切到其他岗位，再从刚结束的销售会议详情导出。导出文件包含销售模板的五个维度、主问题和评分依据，基础信息栏写明模板名称。
3. 不选模板开会并导出，文件注明"未提供本场模板"，并保留实际问答。
4. 招聘模式下准备一份 JD，以及已上传的旧评分卡、评分标准、练习题各一份。四份资料写入相同的检索主题和各自唯一的标记。分别发起会中回答请求和会后纪要请求：两条路径都命中 JD 标记，都不含另外三个标记。
5. 用面试官提问和候选人回答恰好落在相邻分段的长转写导出，核对问答归属、说话人和引文。现有分段导出会对每段单独调用模型；如果归属出错，在技能说明中补充"跨段时以说话人标签和顺序配对"，不另建合并服务。

## 第二阶段：复制预置模板后改文字

1. 在"模式设置 → 招聘 → 岗位面试模板"中，并列展示预置模板和用户保存的模板。用户可以从预置模板复制出一份，修改名称、主问题和各分数锚点的文字，并增删维度。
2. 用户模板存在新的 `interview_templates` 表中，含 `id`、名称、内容 JSON 和 `updated_at`。预置模板不可修改。
3. 会议记录仍只保存模板 `id`。导出时读取模板当前保存的内容，报告写入模板名称和"最后修改时间"，事后可以据此判断用的是哪一版标准。模板更新后重新导出，会得到按新标准整理的新文件。
4. 用户模板被删除后，导出按"未提供本场模板"处理，并注明原模板已删除。

## 第三阶段：会中题单与经历追问（需先满足前置条件）

**前置条件（逐项解决后再实施）：**

- **声道。**（2026-11-22 已定）首版只支持线上面试：候选人走系统音频（interviewer 声道），面试官走麦克风。线下面对面时双方都进麦克风，会被招聘模式的声道过滤全部丢弃，暂不支持。
- **冲突规则。**（2026-11-22 已定）保持现有"先比置信度、再比优先级"的规则，不要求政策卡优先。同一片段命中政策问题时，检测器直接不再提交经历追问卡。
- **经历追问卡的隐私审查。**（2026-11-22 已处理）移除原因推断为：由面试官自己的提问触发、接续生成候选人评估汇总、采纳记录写入会后辅导。恢复版改为由候选人回答触发；不接续、不写入会后记录、不改意图映射，也不新增遥测字段。

**内容（按顺序交付）：**

1. **静态题单。** 会中在浮窗展示本场模板的主问题列表，由面试官手动勾选"已问"。勾选结果存入 `meetings` 表新增的可空列 `interview_asked_dimensions_json`（已勾选的维度 id 数组），沿 `interview_template_id` 同一路径保存。导出时与模板一并读取，拼入技能输入，技能据此把已问但转写中没有回答的维度标为"待澄清 · 已问未答"。不调用模型，不自动判断。
2. **经历追问卡。**（2026-11-22 已单独实施）恢复 `candidate_experience_probe`：由候选人回答触发，语义判定确认回答缺少个人行动、判断依据或沟通影响之一时才出卡，回答已充分或尚未说完时保持安静。卡面显示固定文案和候选人原话；面试官按 Tab 后生成一句中立问句，并用「」引用候选人原话。输出校验要求只有一个问句、引文能在转写中逐字找到，并且不含录用判断或敏感属性，不通过时回落到兜底问句。候选人继续作答（片段不少于 15 字）时，撤下尚未采纳的追问卡并重新判定。
3. **自动开题与覆盖跟踪（视静态题单试用反馈再决定）。** 包括开场直接显示首题（需新增不依赖转写的触发路径和卡片类型）、按覆盖状态自动提示下一题、识别面试官的同义提问。

经历追问的预期表现，例如面试官问"发现项目可能延期后，你是怎么处理的？"：

| 候选人的回答 | 预期表现 |
|---|---|
| "最后我们协调好了，按时上线了。" | 追问个人行动："你发现可能延期后，先做了什么？" |
| "我看到一次接口超时，当天决定先观察。" | 追问判断依据："当时有哪些信息让你决定先观察？" |
| "我确认会晚两天，给产品经理发了两个排期选项。" | 如果前文关注的是协调，追问沟通影响："产品经理收到选项后，怎么决定的？" |
| "我复现后确认会晚两天，给产品经理发了两个选项，她选了拆分上线。" | 保持安静。这段回答已交代如何判断、采取了什么行动，以及沟通带来的结果。 |

评分项空缺、停顿、表达流畅或疑似接受过面试训练，都不足以触发追问。卡片只补问事实，不推断性格、诚信或录用倾向。日志和遥测只使用已有的脱敏字段。

## 五套预置岗位模板

适用于业务面和专业面。五套模板均按表中顺序提问。会后由面试官对照下列行为评分，每个分数附候选人原话和转写位置。1 分表示有具体事例显示做法明显低于要求，2 分表示只完成部分关键动作，3 分达到本轮要求，4 分表示有进一步验证或改进的证据。完整转写中未涉及的维度标"未覆盖"；谈到了但关键事实仍不清楚的标"待澄清"，两者都可以不评分。候选人主动谈到的事实也计入覆盖。锚点是校准示例，等效做法同样可以作为证据。

| 需求澄清 | 选一个“系统要更灵活”之类的模糊诉求。你最终怎么定义需求？ | 直接承诺开发，业务目标仍有争议 | 写明功能，业务边界仍靠口头理解 | 明确角色、触发条件、规则和验收示例并取得确认 | 用边界案例暴露冲突规则，推动业务方明确取舍 |
| 方案适配 | 讲一次客户要求定制而标准功能能覆盖部分需求的经历。最后怎么选？ | 已知标准能力可用仍未经评估就承诺定制 | 演示过标准功能，只按初期开发量比较 | 比较标准配置、流程调整和定制的业务影响及维护成本 | 用客户样本验证关键差异，说明验证如何影响决定 |
| 业务验收 | 讲一个已交付的流程。业务方凭什么确认它可投入使用？ | 以界面演示通过替代业务验收 | 仅走通正常路径 | 由关键用户用代表性数据核对端到端结果及异常处理 | 验收发现偏差后追到根因，修正并组织复验 |

### 企业系统项目经理

| 评估维度 | 标准主问题 | 1 分 | 2 分 | 3 分 | 4 分 |
|---|---|---|---|---|---|
| 范围控制 | 讲一次实施中途新增需求。你如何决定是否纳入本期？ | 未核实影响便承诺范围、日期均不变 | 记录了变更，资源冲突到执行时才处理 | 评估工期、成本和依赖，推动授权方取舍并更新基线 | 核对变更的实际影响，并据此改进后续估算 |
| 排期与依赖 | 讲一次上线日期已定、关键依赖却可能延期的经历。你怎么重排？ | 已知依赖阻断仍按原计划分派任务 | 调整局部排期，漏掉下游联动 | 找出受影响里程碑，明确备选路径、负责人和期限 | 在触发点启用备选方案，复核关键路径及剩余余量 |
| 风险沟通与决策 | 讲一次必须在信息不完整时上报的项目风险。你怎样推动决定？ | 明知需跨部门决定仍拖到窗口关闭 | 发出风险通知，未提出需要谁何时决定 | 区分已知与未知，列出选项、决策人和截止时间 | 追踪决定是否执行，风险变化后及时再次协调 |
| 上线与移交 | 选一次上线。谁决定可上线，你如何组织验收、切换及移交？ | 明知关键条件未满足仍跳过审批切换 | 完成上线清单，遗留事项无人接手 | 明确准入条件、回退安排、遗留责任及运维接收 | 通过演练或分批切换发现问题，修正并验证接手效果 |

顾问兼项目经理岗在第二阶段通过复制模板，提前把方案设计与项目交付维度保存为一份兼岗模板。会前只选这一份，可用同一项目案例分别核实两种责任。

### 开发工程师

| 评估维度 | 标准主问题 | 1 分 | 2 分 | 3 分 | 4 分 |
|---|---|---|---|---|---|
| 故障定位 | 讲一个最初判断错了原因的故障。哪条证据改变了你的判断？ | 反复修改多个变量，无法辨别哪项起效 | 能复现症状，靠多次试改缩小范围 | 用日志、复现或对照实验排除假设并验证根因 | 同时解释原判断为何看似成立，并补上能提前发现复发的检查 |
| 技术取舍 | 讲一个有两种可行实现的改动。你们最后选了哪种，为什么？ | 已知方案违反关键约束仍直接采用 | 比较了实现成本，忽略已知的运行约束 | 结合实际负载、维护成本或兼容性解释取舍 | 用测量或试验验证关键假设，指出何时需要重选 |
| 交付质量 | 选一次有兼容性或数据风险的发布。你如何让改动安全落地？ | 对已知高风险路径未经验证直接全量发布 | 验证了正常路径，遗漏已识别的失败情形 | 针对具体风险验证边界、兼容和失败恢复，并检查上线表现 | 演练恢复或分批验证，根据观测结果调整发布 |
| 结果验证 | 讲一次性能或可靠性改进。你怎样确认它在真实使用中有效？ | 仅凭本机体验宣布线上问题解决 | 有前后数值，但负载或样本不同 | 用可比基线和线上观测说明改善程度及局限 | 检查长尾或资源代价，并据此调整实现或运行策略 |
