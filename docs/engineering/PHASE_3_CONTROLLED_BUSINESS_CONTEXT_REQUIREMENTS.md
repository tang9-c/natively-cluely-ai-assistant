# Phase 3: 受控业务系统只读上下文需求

## 目标

让 Natively 在会议中按用户明确要求，读取 PLM/QMS 等受控业务系统里的只读上下文，并把结果用于回答。

Natively 不替代 PLM/QMS，不写回业务系统，不暴露 MCP 概念给普通用户。

一句话：

当用户明确说“根据 PLM/QMS/业务系统回答”时，Natively 可以用用户已配置的业务系统知识源查找相关信息，并基于返回结果给出只读回答。

## 定位

- 这是“受控业务系统上下文”能力，不是通用 MCP 平台。
- MCP 是内部连接方式，不是用户可见产品名。
- 对外展示为：
  - PLM 知识源；
  - QMS 知识源；
  - 业务系统知识源；
  - 受控业务系统上下文。
- 第一版只读，不做任何写回、创建、审批或修改操作。

## 触发方式

第一版只支持一种触发：

用户明确要求使用业务系统知识源。

示例：

- “根据 PLM 回答。”
- “查一下 PLM。”
- “用 QMS 确认一下。”
- “去系统里看一下。”
- “根据业务系统知识源回答。”
- “查一下物料 a12345 是什么状态。”
- “查一下 B55 项目进度怎么样，是谁负责。”

第一版不做：

- 自动根据 BOM、ECO、CAPA 等关键词触发；
- 自动根据对象编号触发；
- 自动根据会议类型触发；
- 自动根据屏幕内容触发；
- 后台预判用户可能需要业务系统信息。

触发判断必须规则优先。第一版用明确短语判断，例如“根据 PLM”“查一下 PLM”“用 QMS 确认”“去系统里看一下”“业务系统知识源”。

第一版不使用 LLM 从整段会议中判断是否触发业务系统查询，避免误触发和不可测行为。

## 查询信息获取

用户不需要提供精确对象 ID 或结构化查询条件。

但用户必须提供足以形成自然语言查询的业务线索，例如：

- 物料号或近似编号；
- 项目名；
- 图纸名；
- 需求名称；
- 问题描述；
- 质量事件描述；
- 变更描述；
- 最近会议上下文里刚刚提到的业务对象。

Natively 从以下范围整理查询：

- 用户本轮问题；
- 最近一小段会议上下文。

如果信息足够，Natively 将自然语言查询交给对应 MCP 连接器。

如果信息不足，Natively 不查询、不猜测，而是追问用户补充。

发送给 MCP 的上下文必须最小化：

- 默认只发送用户本轮问题；
- 需要消解“这个”“刚才那个”等指代时，可以附带最近上下文摘要；
- 最近上下文摘要最多 1-3 句；
- 不发送完整会议 transcript；
- 不发送屏幕内容；
- 不发送上传资料正文；
- 不发送用户凭据。

## 职责边界

Natively 负责：

- 判断用户是否明确要求查业务系统；
- 判断是否有最小可查询线索；
- 整理自然语言查询；
- 调用受控只读连接器；
- 将连接器返回结果作为回答上下文；
- 在查不到、认证失败、结果不唯一、信息不足时明确说明，不编造答案。

MCP 连接器负责：

- 模糊搜索；
- 对象匹配；
- 系统内查询；
- 权限判断；
- 返回查询结果。

业务系统负责：

- 决定当前凭据能看到什么数据；
- 拒绝无权限访问；
- 返回真实业务数据。

## MCP 协议边界

第一版真实接入 MCP 协议，但只支持 Streamable HTTP MCP endpoint。

第一版不支持：

- 本地 stdio MCP；
- 用户填写本地命令；
- 任意 MCP server 管理；
- 任意 MCP tool picker；
- 让模型自行选择 MCP tool。

为了保证只读边界和实施可控，第一版要求业务系统 MCP endpoint 暴露固定只读工具：

```text
business_context.query
```

Natively 只调用这个工具。

即使 MCP server 暴露其它工具，例如创建、更新、审批或删除类工具，Natively 也不能调用。

### `business_context.query` 输入

```json
{
  "query": "查一下物料 a12345 是什么状态",
  "sourceHint": "plm",
  "recentContext": "可选的最近上下文摘要"
}
```

字段说明：

- `query`：必填，自然语言业务查询。
- `sourceHint`：可选，来自用户触发词或知识源类型，例如 `plm`、`qms`、`business_system`。
- `recentContext`：可选，只能是最小化后的最近上下文摘要。

### `business_context.query` 输出

MCP 工具必须返回可解析的结构化结果。Natively 只信任该结构化结果，不让模型解释任意 MCP 原始文本。

最小契约：

```json
{
  "status": "ok",
  "sourceName": "PLM 知识源",
  "summary": "物料 a12345 当前可用，负责人是张三。",
  "items": []
}
```

`status` 必须是以下值之一：

- `ok`；
- `no_result`；
- `ambiguous`；
- `auth_failed`；
- `unavailable`；
- `timeout`；
- `error`。

`sourceName` 用于回答中说明信息来源。

`summary` 是业务系统返回的只读摘要。主回答可以基于它组织语言。

`items` 可选，用于连接器返回多个候选对象或结构化条目。第一版不要求主回答默认展示对象编号、版本、状态和时间戳。

## 认证方式

第一版支持两种认证方式：

1. 用户名 + 密码。
2. API Key。

产品上表现为：

- 连接 PLM 知识源；
- 连接 QMS 知识源；
- 认证方式：账号密码 / API Key。

Natively 只负责安全保存和传递凭据给受控连接器。

权限判断由连接器和背后的业务系统完成。

凭据保存复用当前 `CredentialsManager` 的既有方式，不在本阶段新增加密改造。

凭据要求：

- 不进入 prompt；
- 不暴露给模型；
- 不出现在日志；
- 不出现在答案；
- 不出现在引用详情；
- 仅用于只读查询。

## 回答方式

主回答保持轻量。

默认只说明信息来源，例如：

- “根据 PLM 知识源……”
- “QMS 知识源显示……”
- “我没有从已连接的业务系统知识源中确认到这个信息。”

第一版不要求主回答默认展示：

- 对象编号；
- 版本；
- 状态；
- 更新时间；
- 查询时间；
- 权限范围。

这些可以作为内部记录、引用详情或后续增强，不作为第一版主回答必需内容。

业务系统查询失败时，以下状态由 Natively 直接给出固定降级回答，不交给 LLM 发挥：

- 缺少查询线索；
- 认证失败；
- 查询超时；
- 查询无结果；
- 查询结果不唯一；
- 知识源不可用；
- MCP 工具返回错误。

成功查询才进入主回答链路。成功结果作为 `business_system` 上下文候选进入实时上下文编排。

## 范围

第一版优先支持 PLM/QMS 相关场景，但不把对象类型写死。

优先覆盖：

- 物料；
- BOM；
- ECO/ECN；
- 项目；
- 图纸；
- 需求；
- CAPA；
- NCR；
- 偏差；
- 问题单；
- 审批、负责人、进度状态。

但产品边界应表达为：

受控业务系统里的只读业务记录上下文。

而不是只支持某几个固定对象类型。

## 失败与降级

以下情况必须明确说明，不能编造：

- 用户没有配置对应知识源；
- 认证失败；
- 连接器不可用；
- 查询超时；
- 查询结果为空；
- 查询结果不唯一；
- 用户问题缺少查询线索；
- 业务系统拒绝访问。

示例：

- “我可以查 PLM，但现在还缺少要查询的物料、项目、图纸或变更线索。”
- “PLM 知识源当前不可用，无法确认该信息。”
- “QMS 返回了多个可能结果，需要你指定是哪一个。”
- “我没有从已连接的业务系统知识源中确认到相关信息。”

## 明确不做

第一版不做：

- 写回 PLM/QMS；
- 创建或审批记录；
- 修改 BOM、物料、项目、图纸、需求或质量记录；
- 通用 MCP server 管理界面；
- 让普通用户配置任意 MCP tool；
- 本地 stdio MCP；
- 任意 MCP tool picker；
- 让模型自行选择或调用 MCP tool；
- 自动触发业务系统查询；
- 屏幕 OCR 触发；
- 会议类型触发；
- 大范围多系统搜索；
- Natively 自己实现权限判断。

## 技术实施边界

第一版采用最小真实 MCP 接入方案，先打通主回答链路。

核心模块建议：

- `BusinessSystemKnowledgeSource`：业务系统知识源配置对象，包含名称、类型、URL、认证方式、启用状态和默认标记。
- `BusinessSystemTriggerDetector`：规则判断是否显式触发，并整理自然语言查询。
- `BusinessMcpClient`：只支持 Streamable HTTP MCP，只调用 `business_context.query`。
- `BusinessSystemContextService`：负责触发判断、查询整理、MCP 调用、状态归一和固定失败回答。
- `RealtimeContextOrchestrator`：新增 `business_system` 来源，成功时把业务系统摘要纳入主回答上下文。
- `AnswerContextTrace`：记录业务系统是否使用、知识源名称和查询状态，不记录凭据或长正文。

运行时流程：

1. 用户触发主回答。
2. Natively 用规则判断是否明确要求业务系统知识源。
3. 未显式触发时，完全跳过业务系统查询。
4. 显式触发后，从本轮问题和最小最近上下文摘要整理自然语言查询。
5. 查询线索不足时，直接返回补充线索提示，不调用 MCP。
6. 查询线索足够时，调用默认或匹配到的 HTTP MCP 知识源。
7. MCP 返回 `ok` 时，结果转为 `business_system` context candidate，进入 `RealtimeContextOrchestrator`。
8. MCP 返回失败状态时，Natively 给固定降级回答，不让模型编造。

## 验收标准

- 用户说“根据 PLM 查一下物料 a12345 是什么状态”，Natively 能调用 PLM 知识源并基于返回结果回答。
- 用户说“查一下 B55 项目进度怎么样，是谁负责”，Natively 能把自然语言查询交给业务系统知识源。
- 用户只说“根据 PLM 回答一下这个怎么样”，且最近上下文没有明确业务线索时，Natively 会追问，而不是猜。
- 用户只说“这个项目进度怎么样”，没有明确要求查 PLM、QMS 或业务系统知识源时，Natively 不触发 MCP 查询。
- 认证失败时，Natively 明确提示知识源认证失败或不可用。
- 查询无结果时，Natively 明确说明没有从业务系统确认到信息。
- 查询结果不唯一时，Natively 要求用户补充或指定，不选择其中一个编造确定答案。
- 查询超时或知识源不可用时，Natively 明确说明无法从业务系统确认。
- MCP server 暴露写工具时，Natively 仍然只调用 `business_context.query`。
- 所有业务系统查询都是只读，不存在写回调用。
- 回答中不会暴露用户名、密码、API Key 或任何凭据内容。
- Prompt、answer trace、citation、日志和 renderer 返回值中都不会出现用户名、密码或 API Key。
